**A02-01 — 古い表示からの削除が、未表示の新しいクラウド版を削除する**

- **Severity：P0**
- **修正必須：はい**

**根拠**

`apps/web/src/pages/Gallery.tsx:226`の作品詳細取得は`projectId`だけを契機とする。バックグラウンド同期で一覧データが変わっても、詳細画面の`project`は更新されない。削除時は同ファイル`:433`からIDだけを渡す。

`packages/persistence/src/index.ts:343`の削除APIは、画面が表示していた版を受け取らず、`:351`で現在のIndexedDB行を読み出して削除待ちにする。同期処理`:190`は、その行の新しい`baseVersion`を削除RPCへ渡す。

SQLの`supabase/migrations/20261006132251_project_storage_security.sql:165`は渡された版だけを比較するため、この削除を正常処理する。

**再現方法・結果**

1. 端末Bで作品version 1を読み込み、表示内容を保持する。
2. 端末Aで同じ作品を変更し、version 2を同期する。
3. Bの再接続などで同期を実行する。IndexedDBはversion 2になるが詳細表示はversion 1のまま。
4. Bの古い詳細画面から削除する。

実サービスとメモリ内クラウドで、次を確認した。

```text
表示していたversion = 1
削除に使用されたversion = 2
cloudDeleted = true
バックアップに残る作品数 = 0
新しい版を保護する通知 = なし
```

**影響**

利用者が確認していない新しい変更が削除される。DBにはtombstoneが残るが、通常の作品一覧・バックアップから消え、アプリ内の復元導線はない。仕様4節の新版保護、および`docs/sync.md:49`の「古い削除を取り消し、新しい作品を確認してから再削除する」動作を満たさない。

**推奨修正**

削除要求に表示時点のrevision／versionを含め、IndexedDBトランザクション内で比較する。不一致なら削除せず、最新版を表示して確認し直せるようにする。画面の購読更新だけでは確認中の競合を防げないため、サービス側の比較も必要。

**再テスト項目**

- 詳細表示後、別端末の変更を同期してから削除。
- 削除確認ダイアログを開いている間の更新。
- 同一ブラウザーの別タブからの更新。
- 変更がない作品の通常削除、オフライン削除と再接続。

**A02-02 — 素材の上書き公開とCacheFirstが整合せず、更新後も旧素材を使用する**

- **Severity：P2**
- **修正必須：はい**

**根拠**

`tools/asset-pipeline/build.mjs:110`は承認済み素材を同じファイル名へ上書きし、`:111`のURLにはhash／revisionを付けない。背景・フレームも`:119`で同じURLへ上書きする。

`apps/web/src/sw.ts:36`はこれらを固定名`island-art-v1`のCacheFirstで保持し、`:41`の期限は90日。`packages/content-schema/src/index.ts:238`も固定URLを組み立て、カタログの`assetUrl`を解決に使わない。

**再現方法・結果**

1. 線画を取得してキャッシュする。
2. 同じIDの素材設定を変更した応答へ切り替える。
3. 同じ設定の新しいWorkbox戦略インスタンスで再取得する。

実ローダーと実Workbox戦略を使ったメモリ内検査で、サーバー側の`texture`を`0.35 → 0`に変更しても、取得結果は`0.35`だった。ネットワーク取得回数は初回の1回だけだった。

**影響**

承認後の素材修正が既存利用者へ届かず、新規端末と既存端末で描画結果が異なる。アプリの更新操作だけでは固定名の素材キャッシュが更新されない。これは承認待ちの問題ではなく、承認済み素材を再公開する際の更新契約の問題。

**推奨修正**

素材URLにcontent hashまたはrevisionを付け、ローダーがそのURLを使用する。形式を示す`schemaVersion`と素材の更新世代を区別し、既存作品が参照する素材の保持方針も明示する。

**再テスト項目**

- 線画の素材設定、背景、フレームを同じ論理IDで更新。
- 更新前から利用する端末と新規端末の取得結果比較。
- Service Worker更新後の素材取得。
- 旧作品のオフライン再編集と必要素材の保持。

**A02-03 — 古いクラウドサムネイルが最新作品のものとして固定される**

- **Severity：P2**
- **修正必須：はい**

**根拠**

`packages/persistence/src/cloud.ts:42`と`:46`は、作品versionを含まない固定パスでサムネイルを送受信する。

`packages/persistence/src/index.ts:435`で取得した画像は、`:442`で現在のローカル作品revisionに関連付けられる。画像がどのクラウド版から生成されたかは確認できない。一度関連付けると`:433`でローカル画像を返し続ける。

作品状態を先に同期する経路は`apps/web/src/pages/Editor.tsx:251`などにあり、サムネイル生成は別途予約される。

**再現方法・結果**

1. Aから赤い作品状態と赤いサムネイルを同期し、Bで取得する。
2. Aから青い作品状態だけを先に同期する。
3. Bで同期・サムネイル取得を行う。
4. Aから青いサムネイルを追加同期する。
5. Bで再同期・再取得する。

実サービスで次を確認した。

```text
Bの作品状態 = 青
クラウドのサムネイル = 青
Bが返すサムネイル = 赤
後続の同期後も赤
```

**影響**

一覧が実際の保存内容と食い違い、更新済み作品を古い作品と誤認させる。作品状態自体は保持されるが、保存結果を確認する主要表示が継続的に誤る。

**推奨修正**

サムネイルの送受信契約に作品versionまたは描画状態hashを含め、一致した画像だけを採用する。対応する画像がない場合は作品状態から再描画し、旧画像を現在のrevisionとして記録しない。

**再テスト項目**

- 状態同期後にサムネイル送信を遅延・失敗させる。
- 別端末で旧画像を取得した後、最新画像を公開する。
- 再起動後のキャッシュ、競合複製、背景・フレーム変更。
- 最新画像がない場合の状態からの再描画。

**A02-04 — 1回の塗り保存で全作品のサムネイル本体を読み出す**

- **Severity：P2**
- **修正必須：はい**

**根拠**

`packages/persistence/src/index.ts:339`から呼ばれる`changed()`は、`:74`で`refreshCount()`を実行する。`:63`は同期待ち件数を数えるために、全作品と全サムネイルを`getAllFromIndex()`で取得する。

サムネイルは`packages/persistence/src/local.ts:17`でArrayBufferとして保存されるため、件数計算だけでも画像のバイト列全体が読み出される。画面の塗り操作は`apps/web/src/pages/Editor.tsx:208`で毎回保存を要求する。

**再現方法・結果**

fake-indexeddbに500作品と各64KiBのサムネイルを用意し、実サービスで1領域を3回保存した。各回、次の取得を確認した。

```text
projects：500行
thumbnails：500行、32,768,000 bytes
3回のサムネイル取得合計：98,304,000 bytes
```

1回あたり31.25MiBを、同期待ち件数の算出のために取得している。

**影響**

塗り保存の負荷が、編集中の1作品ではなくアカウント全体の画像容量に比例する。500作品を許容する構成で、連続タップによる不要な読み出し・コピー・GC負荷が増える。実機でのフリーズ時間やFPS低下は未計測だが、不要な画像本体取得は再現済み。

**推奨修正**

同期待ち管理を画像本体から分離し、軽量なoutbox／メタデータの索引またはトランザクション内で維持する件数を使用する。保存ごとの件数更新でサムネイル本体を取得しない。

**再テスト項目**

- 500作品・サムネイル付き状態で連続保存。
- 件数更新が画像本体を読み出さないことの検査。
- サムネイル容量を増やしても保存処理の取得量が増えないこと。
- 中価格帯Androidで入力応答、長いタスク、メモリ使用量を計測。
